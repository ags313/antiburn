# Installing the agent shell locally

These steps install locally assembled candidates, not published products. Build with `node scripts/assemble-antiburn-shell.mjs` and use the absolute artifact path for your checkout. Review package contents and hashes before enabling executable adapters.

## Before installing

1. Choose one source and scope. Retire the confirmed old owned antiburn skill using the [targeted instructions](migration.md#retire-the-owned-standalone-skill). Never overwrite unrelated installations or replace an existing settings file wholesale.
2. Test in separate temporary host profiles and disposable projects. Leave active `antiburn-mod` release sessions and their profiles alone.
3. Help does not require the desktop app, an executable on PATH, or an antiburn account. Model-mediated commands still need normal host model access. A missing executable is an expected state.
4. Verify help/status, shell version, `App connection: Not checked`, reload, and removal. A file copy alone is not proof of native operation. Use the runtime versions documented by each artifact.

## Claude Code

Use the [unified plugin guide](../../plugins/antiburn/README.md) for the local
0.2.0 candidate, and the [migration guide](migration.md) before changing an
existing `antiburn-mod` installation. One-session loading uses:

```sh
claude --plugin-dir ./plugins/antiburn
```

This is the same self-contained artifact generated by the Claude builder; the
cross-agent assembler delegates to that builder rather than producing a second
public Claude runtime. Public usage/help/refresh commands never require Node, an antiburn
executable or the desktop app. CLI discovery belongs only to development builds.

The following other-agent installation notes are unpublished candidate runbooks.
Their native acceptance and release remain deferred. Use separate temporary
profiles and leave existing user skills/configuration intact.

## Codex

The default package is a skill with no lifecycle hooks. It checks on explicit invocation, not automatic startup.

```sh
codex plugin marketplace add /absolute/artifacts/antiburn-shell/catalogs/codex
```

On Codex CLI 0.159.0, install with `codex plugin add antiburn@<catalog-name>` and inspect with `codex plugin list`. Use a dedicated temporary `CODEX_HOME` during testing. In the supported desktop client, find the catalog entry in Plugins, inspect it, and install/enable it; desktop installation is a separate acceptance gate. Invoke through `/skills` or its installed `$` name. Record the actual qualified spelling; a native `/antiburn` slash command is not promised.

Repository catalogs use `.agents/plugins/marketplace.json`, with source paths relative to the marketplace root. A trusted project's `.codex/config.toml` can control a matching local plugin key. Merge only owned entries; preserve other config. Workspace/admin policies can restrict installation.

On CLI 0.159.0, remove with `codex plugin remove antiburn@<catalog-name>`. Disable/remove through the desktop client's package controls when installed there. For a manually owned catalog, remove only its entry and unchanged artifact after disabling. Do not install the test package into this running chat's shared profile. Loose-skill installation needs its own client-specific location and precedence validation.

## Cursor

The UI’s From Local Repository importer requires the generated catalog root to be a real Git repository with its own commit. Importing an ignored catalog subdirectory from another repository can appear successful before a Git-fetch error appears. Use a disposable Git snapshot for acceptance and verify the loaded detail page after installation. Use a distinct catalog identity when changing sources; reimporting the same identity can retain its previous source.

For local testing, copy the complete assembled Cursor artifact into the isolated profile's `plugins/local/antiburn` directory. The normal user location is `~/.cursor/plugins/local/antiburn`; do not modify that live location during acceptance. Include the hidden `.cursor-plugin` directory. External symlinks may be skipped.

Restart the isolated client or run Developer: Reload Window. Inspect Customize and select `/antiburn` in Agent chat. This explicit-only skill replaces our old standalone findings skill; remove the old owned copy before loading the candidate. Local imports need organizational permission; do not bypass policy. A same-name marketplace install can take precedence over the local copy.

Once a verified listing exists, use Customize → listing → Install → user or project scope. A team admin can import the generated catalog through Dashboard → Plugins & MCPs → Team Marketplaces, review it, and expose it as Default Off. This implementation creates no listing or team import.

Update only the owned local artifact; remove only that directory and reload. Marketplace installs use Customize controls, subject to policy. Automatic startup is unsupported until execution and user-visible output are independently established; explicit command use remains available.

## OpenCode

Install the explicit command asset separately from the runtime candidate. Copy `opencode/commands/antiburn.md` into one scope:

- User: `~/.config/opencode/commands/antiburn.md`.
- Project: `.opencode/commands/antiburn.md`.

Use a disposable project/profile first. Refuse a conflicting file. Start a new TUI session and invoke `/antiburn`. A prompt-based response can consume model capacity.

For the opt-in runtime candidate, merge this entry into the selected scope's existing `opencode.json` `plugin` array, using your actual absolute file URL:

```json
{
  "plugin": [
    "file:///absolute/artifacts/antiburn-shell/opencode/runtime/antiburn.mjs"
  ]
}
```

Preserve all adjacent `lib/` files. This loading path was exercised against OpenCode 1.19.2's local server API; TUI visibility remains a separate gate. Use a dedicated `HOME` and XDG config/data/cache/state directories for acceptance. Remove only this array entry to disable the candidate. For npm installation, merge only the verified pinned package into the existing `plugin` array; no published package is assumed here. An npm plugin does not automatically install command assets.

If startup notice behavior is unverified, use the explicit command and report that limit. Update/remove owned command/runtime files and config entries only; preserve unrelated JSON, commands, and the shared cache. Registry publication and name ownership are separate gates.

## Pi

Load the complete artifact through its entry for one-session testing:

```sh
pi --extension /absolute/artifacts/antiburn-shell/pi/extensions/antiburn.mjs
```

Keep adjacent shared files. Alternatively install the local package:

```sh
pi install /absolute/artifacts/antiburn-shell/pi
pi list
```

Set `PI_CODING_AGENT_DIR` to a temporary profile and use a disposable working directory during testing. Personal scope is the default. Explicit `--local` installation writes project declarations and needs project trust. Review source before granting trust.

Invoke `/antiburn` for help/status and verify the notice without a model request. Startup belongs at `session_start`, not factory discovery. Reload must not duplicate the same session's notice. See the artifact for presentation overrides.

Remove with `pi remove <exact-installed-source>` in the matching scope, restart, and verify command removal. One-session users stop supplying the flag. On Pi 0.80.3, `pi update --all` reconciles installed packages; a pinned version/ref needs an explicit new selection to upgrade.

## Updates, rollback, and evidence

Record artifact hash/version, source, scope, host build, OS, surface, activation, result, and removal. Test a synthetic executable that would create a marker if launched; the marker must stay absent. Native color needs visual evidence on light/dark surfaces; a palette function alone does not prove presentation.

Rollback selects a retained verified artifact through the same host install path. Do not mutate a published version. These instructions authorize no tags, submission, publish, or release draft. Plugin removal does not uninstall the desktop app or an existing executable. A future app connection needs a real CLI protocol.

## Cross-vendor visual audit launcher

Run `node scripts/audit-antiburn-shell.mjs prepare` from the source checkout after assembly. It verifies the source inventory and creates a unique temporary audit directory with artifact copies, separate projects/profiles, a Cursor Git catalog, `audit.json`, and `CHECKLIST.md`. Cursor's copied catalog receives a unique name; source hashes describe the original artifacts before this fixture metadata change.

Launch one vendor at a time from an interactive terminal:

```sh
node scripts/audit-antiburn-shell.mjs launch /absolute/audit-dir claude
node scripts/audit-antiburn-shell.mjs launch /absolute/audit-dir codex
node scripts/audit-antiburn-shell.mjs launch /absolute/audit-dir cursor
node scripts/audit-antiburn-shell.mjs launch /absolute/audit-dir opencode
node scripts/audit-antiburn-shell.mjs launch /absolute/audit-dir pi
```

An optional final argument supplies the vendor binary path when it is not on PATH. A per-audit `hosts.<vendor>.binary` entry in `audit.json` selects a persistent local binary; an explicit argument takes precedence. An absolute binary path also puts its directory first on the child's PATH, for runtimes installed beside that binary. No host package is downloaded. Codex's launcher installs the local catalog/plugin into its temporary `CODEX_HOME`. Claude and Pi use one-session flags. OpenCode receives a project command and runtime configuration with isolated HOME/XDG paths. Cursor receives separate user-data and extension directories plus a local plugin candidate. Its local discovery still needs host verification; the checklist includes the manual Git-catalog fallback.

These are separate profiles, not an OS sandbox. Inherited environment values, system credentials and vendor account sync may still apply. The launcher copies no credentials, sends no prompts and captures no screenshots. Sign in manually if needed. A Cursor account import is a manual action that can affect other devices. Codex desktop remains a separate manual gate.

Each launch writes its own `<vendor>-launch.json`; zero exit status never changes visual status from `pending`. Capture and assess the checklist manually. Exit all audit hosts before deleting the temporary directory. The launcher performs no global uninstall or recursive cleanup.
